# Backend guide for MatsyaSetu v3 (step by step)

For the existing FastAPI + PostgreSQL + SQLAlchemy + Alembic repo (`~/projects/fish-project`, auth, trips, handovers, rates, payments with void already exist). Work in small slices. After every slice: tests green, ruff clean, one commit.

Commands are Ubuntu bash. Always read an autogenerated migration before applying it. Never edit old migrations.

## Step 1. Profile and preferences  (what you asked for first)
One profile per owner, with **all** settings stored on the backend so they follow the owner to any phone.

**Tables** (new migration `add_profile_preferences`)
- `owner_profiles`: `owner_id` (PK, FK owners.id), `name`, `phone`, `email`, `preferences JSONB NOT NULL DEFAULT '{}'`, `updated_at`.
- `default_rates`: `fish_type_id` (PK, FK), `rate_per_bag Numeric(10,2) NOT NULL CHECK > 0`. **Write-only** (never returned).
- `fish_type_photos`: `fish_type_id` (PK, FK), `content_type`, `data BYTEA`, `updated_at`. Store in Postgres, not on disk: the Render free disk is wiped on every deploy.

**Preferences JSON** (validate with a Pydantic model, reject unknown keys). Exactly the frontend `Preferences` type:
```
theme: light|dark|system        showRates: bool
defaultSupplierId: int|null     defaultFishIds: int[]
lowStock: { all: int>=0, perFish: { "<fishId>": int>=0 } }
stockAlerts: { enabled, onDashboard, vibrate: bool }
```
Validation rules: supplier must exist and be active; every fish id must exist; numbers 0 to 100000.

**Endpoints**
| Method | Path | Notes |
|---|---|---|
| GET | `/api/profile` | `{name, username, phone, email, preferences, ratesSet:{all, perFish:{id:bool}}}`. Creates the row with defaults on first call. |
| PATCH | `/api/profile` | name, phone, email. Name required. |
| PATCH | `/api/profile/preferences` | Partial body, deep merge, return full preferences. |
| PUT | `/api/default-rates` | `{all?: int, perFish?: {id:int}}`. `all` sets every active fish. Returns flags only. |
| GET | `/api/default-rates/status` | Flags only, never values. |
| POST | `/api/fish-types/{id}/photo` | multipart, max 2 MB in, re-encode with Pillow to JPEG max 256 px, store. |
| GET | `/api/fish-types/{id}/photo` | Returns the image, `Cache-Control: private, max-age=86400`. Or add `photoUrl` to the fish-type response. |
| DELETE | `/api/fish-types/{id}/photo` | |

**Rule:** when a trip is created, copy `default_rates` into `trip_fish_types.rate_per_bag` (existing column). Later changes to default rates never change old trips. Handover lines keep their snapshot (already built).

**Tests:** defaults on first read; deep-merge keeps other keys; unknown key rejected; bad supplier id rejected; rates never appear in any GET; photo over size rejected; photo is re-encoded; unauthenticated gets 401.

## Step 2. Payment rules for the new flow
Frontend flow is **handover first, then current payment. Advance is only before handover.**

In the payment service, inside the same transaction, with `SELECT ... FOR UPDATE` on the `trip_customers` row:
- `kind = ADVANCE`: allowed only if the trip customer has **no active handover** and the trip is not CLOSED. Else 409 `ALREADY_HANDED` / `TRIP_CLOSED`.
- `kind = PAYMENT`: allowed only if an active handover exists (else 409 `NOT_HANDED`). Allowed on a closed trip (collecting later).
- amount: integer or 2-decimal Decimal, > 0, upper limit 10,000,000.
- Same `reference` returns the original payment with `200` and `replay: true` (no second row). Keep your existing unique reference.
- Over-payment is allowed. The balance goes negative and shows as credit (frontend shows "Paid ahead").
- Void: needs reason (min 3 chars), keeps the row, allowed on closed trips. Already built, keep it.

**Expected amount before handover.** Add to the per-customer payments data: `expected_amount` = planned/ordered bags × current rate (null per unpriced fish, and set `rate_missing = true`). After handover use billed amount from handover lines. This is what the Advance sheet shows as "Expected amount".

**Tests:** advance after handover is rejected; payment before handover is rejected; replay does not duplicate; two parallel requests with different references both succeed and the sum is right; overpay gives negative remaining; voided payments are skipped in totals.

## Step 3. Remaining-after snapshot (receipts must never change)
- Add `payments.remaining_after Numeric(12,2) NOT NULL` (migration with backfill).
- On insert, compute `billed_or_expected − sum(active payments incl. this one)` while holding the row lock, store it.
- Backfill: for each trip customer, replay payments ordered by `created_at, id` using the billed amount at the time (use the current billed amount; note it in the migration comment).
- Voiding a payment does **not** rewrite other rows' snapshots. A later receipt shows what was true then.

## Step 4. One call per screen (no N+1 on a phone)
These shapes are in `src/api/types.ts`. Match them.

| Endpoint | Returns |
|---|---|
| `GET /api/trips` | `TripSummary[]`: id, code (`T-YYYY-MM-DD`), date, supplier, status, customers, bags, amount, paid, remaining (sum of positive remainings) |
| `GET /api/trips/{id}/overview` | `TripDetail`: trip summary + one row per customer: lines (fish, ordered, handed, rate or null), orderedBags, handedBags, handedOver, amount, amountFinal, paid, advance, remaining, rateMissing, status + fishTotals + handedCount |
| `GET /api/trip-customers/{tcId}` | `{row, trip, payments[]}` newest first |
| `POST /api/trip-customers/{tcId}/handover` | `{bags: {fishId: n}, note}`. Wraps your existing handover (idempotent submit reference). One handover per customer per trip in this UI. |
| `POST /api/trip-customers/{tcId}/payments` | `{kind, amount, method, note, reference}` → `{payment, replay}` |
| `POST /api/payments/{id}/void` | `{reason}` |
| `GET /api/payments/{id}/receipt` | JSON `Receipt` (see step 6) |
| `GET /api/customers` | list with `outstanding` and `trips` count per customer (one SQL query with GROUP BY) |
| `GET /api/customers/{id}/balances` | `{customer, outstanding, trips:[{tripId, tripCode, date, status, tcId, amount, paid, remaining, rateMissing}]}` |
| `GET /api/payments/outstanding` | `{total, trips:[{tripId, code, date, remaining, customers}]}` |
| `POST /api/trips` | `{supplierId, date, fishIds, orders:[{customerId, bags:{fishId:n}}]}` → creates trip + trip customers + requirements in one transaction; copies default rates |
| `POST /api/trips/{id}/close` | existing rule (blocked while stock left > 0, leftover handed to Self). **Unpaid balances never block closing.** |

**status** per row (compute on the server so every client agrees): `PENDING` (no handover, no advance), `ADVANCE`, `HANDED` (handover, nothing paid), `PARTIAL`, `PAID` (amount > 0 and remaining = 0), `CREDIT` (remaining < 0).

**Rate secrecy:** line `rate` is returned only if `preferences.showRates` is true, otherwise `null`. Amount fields are always returned. This is a convenience against shoulder-surfing, not security. Decide later whether rates should be hidden from the API for good.

## Step 5. Closing note: one rule the UI relies on
The trip screen enables **Close trip** only when every customer has a handover. Your backend rule is "stock left must be 0". Keep both: the UI check is a convenience, the backend check is the truth. If they disagree, show the backend message (frontend already shows `message`).

## Step 6. Receipts and reports (reportlab, pypdf, openpyxl)
```bash
uv add reportlab pypdf openpyxl
```
Create `app/services/documents.py` with pure functions that take plain data and return `bytes`. No DB access inside them (easy to test).

**6a. Payment receipt PDF** `GET /api/payments/{id}/receipt.pdf` (reportlab, A5 portrait)
- Header: MatsyaSetu, receipt number `R-YYYYMMDD-0001`, date and time.
- Customer, trip code, supplier.
- Type (Advance or Current payment), method, **amount received**, trip amount, paid so far, **remaining for this trip** (from the snapshot, step 3).
- If the payment is voided, a red "CANCELLED" band and reason.
- **Gotcha:** the built-in Helvetica has no `₹` glyph. Register a TTF (DejaVu Sans or Noto Sans) with `pdfmetrics.registerFont(TTFont(...))` and ship the font file in the repo.
- Headers: `Content-Type: application/pdf`, `Content-Disposition: attachment; filename="R-....pdf"`, `Cache-Control: no-store`, auth required.

**6b. Trip bundle PDF** `GET /api/trips/{id}/receipts.pdf` (pypdf)
Build each receipt as its own PDF, merge with `PdfWriter.append()`, add bookmarks per customer. Skip voided payments, or mark them clearly (decide with the owner).

**6c. Trip report Excel** `GET /api/trips/{id}/report.xlsx` (openpyxl, `write_only` mode is not needed at this size)
- Sheet "Customers": name, phone, ordered, handed, amount, advance, paid, remaining, status.
- Sheet "Payments": date, customer, kind, method, amount, remaining after, cancelled?, reason.
- Sheet "Fish": fish, ordered, handed, slip bags, left.
- Format money columns as numbers with `#,##0`, freeze the header row, set column widths.
- **Spreadsheet injection:** if a customer name or note starts with `= + - @`, prefix it with `'` before writing.

**6d. Customer statement PDF** (later) `GET /api/customers/{id}/statement.pdf`: each trip with its own balance, then the total.

**Tests:** PDF starts with `%PDF`; `pypdf.PdfReader` can open it and finds the text "Remaining"; the rupee sign is present; xlsx opens with openpyxl and has the 3 sheets; a name starting with `=` is escaped; unauthenticated gets 401.

## Step 7. Make the frontend talk to it
1. Add the endpoint table below to `src/api/api.ts`. Keep the function names.
2. Use `fetch(url, {credentials: "include"})` with your session cookie. Add the exact frontend origin to CORS (credentials on).
3. Errors: return `{code, message}` with the right status. The UI shows `message` and uses `code` for the codes in this guide.
4. Remove `src/api/stub.ts` last. Keep `money.ts` only as a display helper (the server is the truth).
5. Test on a phone: record handover, record payment twice (partial), cancel one, open receipt, share.
